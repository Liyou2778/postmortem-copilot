# 评测方法论：为什么改了三次口径

> 适用项目：Postmortem Copilot（P1）
> 关联：`services/eval/scenarios.py`、`services/eval/runner.py`、`scripts/run_eval.py`

---

## 一、要测什么

产品承诺是"给出可被证据支持的根因 Top3"。所以指标必须回答两个问题：

1. **定位对不对** —— Top-k 里有没有真根因
2. **是不是蒙的** —— 结论有没有证据支撑、有没有真的区分出故障类型

只测第一个会得出虚假的高分，只测第二个会被关键词刷分。

---

## 二、三版口径的演进

### v1：证据包含即命中（错误）

**规则**：结论引用的证据里，只要有一份含故障特征，就算命中。

**结果**：9 个场景全部命中，Recall@1 = 1.000。

**为什么错**：每次只注入一种故障，证据里只有一份带特征。一个"把四份证据全引用上"的模型必然满分。这个指标实际测的是"有没有引用到"，不是"有没有识别对"。

> 这一版是典型的"指标被模型钻空子"。发现方式是看到 1.000 时先怀疑指标，而不是庆祝。

### v2：证据精准率 ≥ 50%（过度惩罚）

**规则**：引用的证据中，带故障特征的必须占一半以上。

**结果**：Recall@1 掉到 0.556。

**为什么错**：看数据才发现，被判失败的两条其实是对的——

| 场景 | 模型输出 | 判定 | 真实 |
|---|---|---|---|
| S001 发布回退 | "v2.31 将连接池上限从 200 降到 50，引发连接争用" | 失败 | ✅ 正确 |
| S003 依赖超时 | "变更窗口内没有任何变更记录，故障更像下游依赖超时，而非本次发布引起" | 失败 | ✅ 正确，还主动排除错误假设 |

一次故障通常有 3–4 份证据**都是合理支撑**，只有一份带"特征字符串"。惩罚引用广度等于惩罚正确的推理。

> 这一版的教训：指标掉分时先看数据，别急着信数字。

### v3：双侧匹配（采用）

**规则**：

```
命中 = 引用了带故障特征的证据（不能空口断言）
       AND 结论里点名了对应故障概念（不能只堆引用）
```

`scenarios.py` 里每类故障定义两组词：

```python
"dns_error": (
    ("no such host", "dns resolution"),        # 证据侧特征
    ("dns", "解析", "域名", "host"),            # 结论侧概念
)
```

**为什么这样能同时挡住两种作弊**：

| 作弊方式 | 被哪一侧挡住 |
|---|---|
| 把所有证据都引用上 | 结论侧：必须说对概念 |
| 背关键词但没证据 | 证据侧：必须引用到带特征的证据 |

## 三、负对照：证明指标不是摆设

一个指标只有在"好模型高分、笨模型低分"时才有意义。所以每次评测都跑一次负对照——用一个只会复读"连接池"的 mock 模型。

| 输入 | Recall@1 | Recall@3 | MRR |
|---|---|---|---|
| 真实模型（DeepSeek，9 场景无噪声） | 1.000 | 1.000 | 1.000 |
| 负对照（复读机 mock） | 0.111 | **0.222** | 0.167 |

同一个指标、同一批场景，差距 4.5 倍。这是这组数字可信的唯一理由。

### 3.1 第一次全量跑出 0.302，查下去是**代码 bug**

63 场景 + 噪声的第一轮结果是 Recall@3 = 0.302。逐条看失败样本，rank1 的诊断**全是对的**：

| 场景 | 模型输出 | 判定 |
|---|---|---|
| 资源饱和 | "CPU 节流达 78%，请求队列被占满" | 判失败 |
| 依赖超时 | "调用 inventory 出现 upstream timeout" | 判失败 |
| DNS 失败 | "DNS 解析重试，上游不可达" | 判失败 |

诊断对却判失败，说明是"证据侧"没通过。定位到 `LogAgent` 的证据摘录：

```text
E-LOG-001: 5 条错误；首条: level=info msg="scheduled job finished in 812ms" svc=reporting
```

**摘录只保留了第一条日志**，而日志是按时间倒序返回的——噪声日志恰好最新，占据了第一条。后果有两个：

1. 判分时证据里找不到故障特征 → 被判失败
2. **更严重**：结论引用了"CPU 节流 78%"，但这个事实不在被引用的证据里——**引用链断了**，违反 FR-7（每条结论必须可回溯）

模型其实是对的：它拿到了完整日志 JSON（prompt 里传了全部），只是我们的证据记录丢了信息。

**修法**：证据摘录保留多行样本（最多 5 行、每条截断 80 字），而不是只取第一条。

修复后同样 9 个噪声场景：Recall@1 从 0.111 升到 **0.889**，Recall@3 到 **1.000**。

> 这条经验比任何分数都值钱：**评测掉分时，先怀疑自己的埋点，再怀疑模型。**
> 而且这个 bug 如果没被评测暴露，线上就会表现为"报告里引用的证据点开看不到那个数字"——一个典型的可追溯性事故。

## 四、场景设计

### 9 类故障

| 故障类型 | 证据形态 | 典型干扰 |
|---|---|---|
| `deploy_regression` | 变更记录含可疑发布 | 无关的扩容变更 |
| `resource_saturation` | 日志含 CPU 节流/内存压力 | 正常流量曲线 |
| `dependency_timeout` | 日志含下游超时 | 拓扑里有个健康的下游 |
| `config_drift` | 变更是 config 而非 deploy | 同期的正常发布 |
| `pod_kill` | 探针失败 + 容器重启 | 实例数只掉 1 |
| `network_partition` | 连接超时/重置 | 其他链路正常 |
| `dns_error` | 域名解析失败 | 其他依赖可达 |
| `io_stall` | fsync 慢、iowait 高 | CPU 不高 |
| `traffic_spike` | QPS 超容量 | 延迟高但服务健康 |

### 噪声模式（`--noise`）

真实事故从来不是单一信号。开启噪声后，DevStack 会额外返回：

- 2 条**无关变更**（别的服务扩容、别人调缓存 TTL）
- 2 条**无关错误日志**（别的服务 cache miss）
- 2 个**健康的下游依赖**

这会显著降低分数——那才是诚实的数字。如果模型把"user-service 扩容"当成根因，说明它没有真正读证据。

### 规模

9 类 × 7 服务 = **63 个场景**。

## 五、指标定义

| 指标 | 定义 | 用途 |
|---|---|---|
| **Recall@1** | Rank1 结论命中 | 主指标，衡量"第一个说的对不对" |
| **Recall@3** | Top3 内有命中 | 产品指标，评审时看这个 |
| **MRR** | 首个命中排名的倒数均值 | 衡量排序质量 |
| **按类型 Recall@3** | 分故障类型统计 | 找出系统性短板 |

**门禁**：`Recall@3 >= 0.70`，否则 CI 失败。

### 5.1 正式结果（63 场景 + 噪声 + 真实模型）

| 指标 | 结果 |
|---|---|
| Recall@1 | **0.603** |
| Recall@3 | **0.857** |
| MRR | 0.714 |
| 总耗时 | 1278s（约 21 分钟） |
| 单场景平均 | 20.3s |

**按故障类型**

| 故障类型 | Recall@3 | 解读 |
|---|---:|---|
| config_drift | 1.000 | 配置漂移特征明确（kind=config） |
| dependency_timeout | 1.000 | 下游超时日志显著 |
| deploy_regression | 1.000 | 变更记录直接点名 |
| dns_error | 1.000 | `no such host` 几乎不可误判 |
| io_stall | 1.000 | fsync/iowait 特征独特 |
| network_partition | 0.857 | 与依赖超时易混 |
| pod_kill | 0.714 | 实例数只掉 1，易被判成资源问题 |
| resource_saturation | 0.714 | 与流量突增症状重叠 |
| **traffic_spike** | **0.429** | **最差：与资源饱和几乎同构，模型倾向归因到 CPU** |

这个分布比总分更有价值——它告诉我们短板在哪：**"资源类"故障的区分度不够**。下一步该给这两类加区分性证据（如 QPS 曲线、限流日志的先后顺序）。

### 5.2 补强：加 QPS 证据（traffic_spike 0.429 → 1.000）

**诊断**：流量突增与资源饱和在延迟曲线上几乎同构。只看延迟，模型无法区分"需求太大"和"容量太小"。

**改动**：`TelemetryAgent` 在拉延迟指标之外，再拉一条 **QPS 指标**并单独成一条证据（`E-QPS-001`）。

| 故障 | QPS | 延迟 |
|---|---|---|
| traffic_spike | **12000**（基准 3000） | 高 |
| resource_saturation | 3000（正常） | 高 |

**结果（14 场景，带噪声，真实模型）**

| 故障类型 | 补强前 | 补强后 |
|---|---:|---:|
| traffic_spike | 0.429 | **1.000** |
| resource_saturation | 0.714 | **0.429** ⚠️ |

**副作用暴露了另一个真问题**：加了 QPS 证据后，资源饱和反而变差。因为它的特征（`cpu throttling`）**只存在于日志证据**，而模型现在更倾向引用指标证据——**引用链断裂**，同一类 FR-7 缺陷的另一种表现。

**结论**：这不是模型变笨，而是"结论引用了事实，但没引用承载该事实的证据"。正确修法不是放宽判分，而是：
1. 在 prompt 里要求"每条事实必须引用其来源证据"；
2. 或做**证据自动绑定**：结论里出现某证据的独有事实（如 `78%`、`cpu`）时自动补引用并标记 `auto-bound`。

这一条留作 M4 的下一步。

## 六、已知局限（必须在面试里主动说）

1. **场景是人工构造的**，不是真实事故回放。特征比真实日志"干净"。
2. **单故障**。真实事故常是多故障叠加，当前场景库不覆盖。
3. **概念词表是人工维护的**，模型换措辞可能漏判（这也是 v1 想避免的问题）。
4. **样本量**。63 个场景够看趋势，不够做统计显著性结论。

### 下一步变难的方向

| 方向 | 做法 |
|---|---|
| 证据缺失 | 故意让某个数据源返回空，测降级能力 |
| 多故障叠加 | 同时注入 2 类故障，考察区分主次 |
| 更强噪声 | 让干扰项在时间上更接近故障窗口 |
| 真实回放 | 接入 Chaos Mesh 后，用真实演练记录做场景 |
