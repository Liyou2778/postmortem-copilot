# 容量评估报告

> 项目：P1 Postmortem Copilot
> 日期：2026-11-21
> 环境：阿里云 ECS 2 vCPU / 4 GiB（华东1 杭州），uvicorn 单进程，
> 压测客户端：独立机器（香港），公网 RTT ≈ 51 ms

---

## 一、方法论：为什么不用 RPS 当结论

这个产品的真实负载是：**每次故障跑一份复盘，一份复盘 ≈ 17–22 秒**（工具调用 + 3–4 次 LLM 请求）。
它既不是高 QPS 的读服务，也不是高并发的写服务。

所以本报告给三层结论：

| 层 | 指标 | 回答什么问题 |
|---|---|---|
| L1 空载开销 | `/healthz` RPS 与延迟 | 框架本身能扛多少请求 |
| L2 业务接口 | 任务创建 / 任务查询 RPS | 常规 API 的承载力 |
| **L3 分析并发** | **同时能跑几个分析** | **产品真正的容量瓶颈** |

**压测必须由另一台机器发起。** 在 2 vCPU 上再跑压测客户端，客户端与服务抢 CPU，
测出的数没有意义（实测本机 loopback 反而只有 204 RPS，就是被客户端拖累的假象）。

## 二、L1 / L2：请求级容量

| 接口 | 并发 | RPS | p50 | p99 | 错误 |
|---|---:|---:|---:|---:|---:|
| `/healthz` | 1 | 17.7 | 51 ms | 64 ms | 0 |
| `/healthz` | 10 | **164.2** | 56 ms | 91 ms | 0 |
| `/healthz` | 30 | 83.4 | 123 ms | 2102 ms | 0 |
| `/healthz` | 60 | 78.2 | 452 ms | 3583 ms | 0 |
| `/healthz` | 100 | 64.1 | 887 ms | 5729 ms | 0 |
| `GET /tasks/{id}` | 10 | 166.6 | 55 ms | 103 ms | 0 |
| `POST /tasks` | 10 | 154.3 | 58 ms | 139 ms | 0（全 201） |
| `POST /tasks` | 30 | 75.6 | 122 ms | 2286 ms | 0 |

**观察**：吞吐在 **c≈10 达到峰值 155–165 RPS**，之后随并发上升而**下降**，延迟线性恶化。

**关键排除项**：压测期间服务器 CPU **6.7%**、内存 490/3563 MB。
**应用不是瓶颈。** 瓶颈在公网路径/连接复用/客户端，不在代码。

> 这个结论本人只能证明到"不是应用 CPU 瓶颈"这一步。要精确定位到 NAT、conntrack
> 还是客户端 GIL，需要第二个 vantage point（例如从同地域另一台 ECS 发起压测），
> 那是下一步的事，不在本报告结论范围内。

## 三、L3：分析并发容量（真正的容量指标）

用 `scripts/probe_concurrency.py` 同时发起 N 个完整分析：

| 并发分析数 | 全部成功 | 墙钟时间 | 最慢单条 | **串行化系数** | 内存 |
|---:|---|---:|---:|---:|---:|
| 1 | ✅ | 19.7 s | 19.5 s | 1.01 | — |
| 2 | ✅ | 17.9 s | 21.6 s | 1.01 | — |
| 4 | ✅ | 18.3 s | 18.1 s | 1.01 | — |
| **8** | ✅ | **17.3 s** | 17.1 s | **1.01** | 490 MB |

**串行化系数 ≈ 1 的含义**：8 个分析同时发起，墙钟时间等于单个分析的时间，
说明它们**真正并行**，没有互相阻塞。

**这意味着**：单个分析的耗时几乎完全由 LLM 往返决定（I/O 密集），
服务器的 CPU 在等待期间是空闲的。这是一个健康的形态。

### 3.1 上限在哪

| 约束 | 估算 | 依据 |
|---|---|---|
| AnyIO 线程池 | **~40 并发分析** | FastAPI 同步端点默认线程池 40，每个 `/run` 独占一个线程 20 秒 |
| 内存 | ~200+ 并发 | 8 并发时 490 MB，每分析增量约 40 MB，4 GiB 可支撑 |
| **LLM 供应商限流** | **实际最先触顶** | DeepSeek 的 QPS/TPM 限额，8 并发时已发 ~24 次请求 |
| CPU | 不构成约束 | 全程 <10% |

**结论：这台机器能同时跑至少 8 个分析且无降级；理论天花板约 40（线程池），
但真实世界会先撞到模型供应商的限流。**

## 四、压测中发现并修复的生产级缺陷

这次压测最重要的产出不是数字，是一个**只有并发才会暴露的架构 bug**。

### 现象

并发发起 2 个分析，第二个返回 **HTTP 500**：

```
app.lease.StaleLease: stale fence for telemetry: presented 6, current 7
```

### 根因

`leases` 表的主键是 **`step_id` 单独**。但本系统里**每个任务的步骤名都是一样的**
（`telemetry` / `log` / `change` / `review`）——步骤 ID 只在任务内唯一。

于是两个并发任务共用同一行租约，互相把对方的 fence 顶掉：

```
任务 A: acquire(telemetry) → fence 6
任务 B: acquire(telemetry) → 覆盖同一行 → fence 7
任务 A: succeed → validate 发现 fence 6 ≠ 7 → StaleLease → 500
```

### 修复

租约按 `(task_id, step_id)` 复合主键隔离；并加了启动时的 schema 迁移
（旧表主键是单列，直接重建——租约是瞬态协调状态，不是业务数据）。

新增两个回归测试：
- `test_two_tasks_with_same_step_names_hold_independent_leases`
- `test_same_step_in_two_tasks_has_separate_fence_counters`

修复后同样的并发探针：**8/8 全部 200，串行化系数 1.01**。

### 为什么这个 bug 值钱

- 单线程顺序执行**永远测不出来**，只有并发才暴露
- 它的表现是 500，不是数据错乱——**如果它表现为数据错乱，就会静默污染复盘结论**
- 它说明"护栏设计对了，但作用域错了"：租约/围栏机制本身正确，错在隔离粒度

## 五、优化建议（按性价比排序）

| # | 建议 | 收益 | 成本 |
|---|---|---|---|
| 1 | **`/run` 改异步**：返回 202 + taskId，后台执行，前端轮询 | 移除 20 秒阻塞请求与 40 线程上限，并发能力提升一个量级 | 中（改接口契约 + 前端 1 个轮询） |
| 2 | 接入队列 + Worker（已有 `SqliteQueue`/`RedisStreamQueue` 与 `StepWorker`） | 分析任务可排队、可重试、可横向扩容 | 中（M3 已建好基础设施） |
| 3 | uvicorn `--workers 2` | 利用第 2 个 vCPU | 低，但**当前 CPU <10%，预计无收益** |
| 4 | 给 LLM 调用加并发信号量 | 主动限流，避免撞供应商限额后被拒 | 低 |
| 5 | 监控 `/metrics` 里任务数与耗时 | 容量可观测，从"测一次"变成"持续看" | 低 |

**建议 3 明确标注为"预期无收益"**：CPU 全程低于 10%，加 worker 只是多占内存。
写进报告是为了说明"我们验证过这条常见建议，在这台机器上不成立"。

## 六点五、SQLite → MySQL 迁移代价量化

**目的**：回答"把数据库从本机文件搬到 RDS，到底付出了什么"。

### 方法论（先说清两个坑）

**坑一：用生产库做基准会得出错误结论。**
第一次测得的 `list_recent` 差距是 **217 倍**，但那是拿"空 SQLite 文件"对比"2400 条、1890 个任务的生产库"。
`GROUP BY task_id` 要扫描的行数差一个数量级——**测的是数据量，不是后端**。
改用独立空库 `copilot_bench` 后，同样指标收敛到 **64 倍**。

**坑二：比值大不等于代价大。**
64 倍听起来骇人，但绝对差是 `2.54ms - 0.039ms ≈ 2.5ms`。
**在 15–20 秒的分析链面前，2.5ms 是 0.01%。** 只看倍数是自欺欺人。

### 第一层：存储层微基准（同一进程，隔离 HTTP/框架）

环境：ECS 本机 2 vCPU，SQLite 用 WAL 文件，MySQL 走内网端点，两边空库起步，
每种操作采样 200 / 100 次。

| 操作 | SQLite p50 | MySQL p50 | 倍数 | 绝对差 |
|---|---:|---:|---:|---:|
| `append`（追加事件） | **2.67 ms** | **5.53 ms** | 2.1x | +2.9 ms |
| `load`（重放 200 事件） | 1.57 ms | 5.63 ms | 3.6x | +4.1 ms |
| `list_recent`（首页列表） | 0.04 ms | 2.54 ms | 64x | +2.5 ms |

### 第二层：HTTP 接口（c=10，8 秒）

| 路径 | SQLite | MySQL | 变化 |
|---|---:|---:|---:|
| 写路径 `POST /tasks` | 151.5 RPS / p50 59.9 ms | **141.3 RPS / p50 63.8 ms** | **-6.7%** |
| 读路径 `GET /tasks/{id}` | 146 RPS¹ / p50 56.5 ms | 146.9 RPS / p50 60.0 ms | 基本持平 |

¹ SQLite 读路径那一次运行的 RPS 字段（75.1）与 p50（56.5 ms）自相矛盾，
说明墙钟计时异常；按「请求数 ÷ 8 秒」复算是 146 RPS，故采信复算值。
**这个异常数据不用于结论**，只记录在此。

### 根因：网络往返是主导项

单独测量 ECS → RDS 的单次往返：

```
SELECT 1                        : 2.22 ms
SELECT MAX(seq) WHERE task_id=? : 2.21 ms
```

于是各项成本可以拆解清楚：

| 操作 | 实测 | 拆解 |
|---|---:|---|
| `list_recent` | 2.54 ms | **2.2 ms 网络往返 + 0.34 ms 查询计算** |
| `append` | 5.53 ms | ~2.5 次往返（`SELECT MAX(seq)` + `INSERT` + `COMMIT`） |
| `load` | 5.63 ms | 1 次往返（2.2 ms）+ 约 3.4 ms 传输 200 行 |

**结论：MySQL 的额外成本 ≈ 每个操作加 1–2 次网络往返，每次 ~2.2 ms。**

### 优化空间（做了评估，未实施）

| 优化 | 预计收益 | 是否值得 |
|---|---|---|
| `append` 合并为单语句 `INSERT ... SELECT MAX(seq)+1` | 5.53 → ~3.3 ms（-40%） | **不值得**：16 条事件 × 2.2 ms = 35 ms，占 15 秒分析链的 0.2% |
| 连接池替代单连接 | 高并发下吞吐提升 | 暂不需要：当前瓶颈是 LLM，不是 DB |
| `leases` 迁到 Redis | 高频短写离开 MySQL | **值得**：租约是唯一高频写，且 Redis 天然带 TTL |
| 给 `events.created_at` 加索引 | `list_recent` 更快 | 低收益：2.5 ms 已经在感知阈值以下 |

**这就是"知道优化点在哪、也知道现在不该做"的判断。** 三条都写进报告，是为了区分
"没发现"和"发现了但没必要"。

### 最终判断

| 维度 | SQLite | MySQL |
|---|---|---|
| 单操作延迟 | ✅ 更优（2–64 倍） | 每次多 2–5 ms |
| **端到端影响** | — | **< 1%（被 LLM 掩盖）** |
| 持久性 | ❌ 随实例磁盘消失 | ✅ 独立存储、有备份 |
| 多实例扩展 | ❌ 文件锁，无法水平扩展 | ✅ 可连接池 / 读写分离 |
| 运维能力 | ❌ 只能 ssh 上去拷文件 | ✅ 控制台监控、慢日志、备份恢复 |
| 可审计 | 弱 | 强（云审计 + 慢查询日志） |

**代价是每个数据库操作 +2~5 ms，换来的是"能扩展、能备份、能审计"。**
对一个单机 demo 这是亏的，对一个要上线的服务这是必须的——
而这正是这次迁移想演示的判断，而不是"越快越好"。

## 七、数据可信度说明
| 项 | 说明 |
|---|---|
| 网络条件 | 客户端在香港、服务在杭州，RTT ≈ 51 ms；同地域压测数字会更高 |
| 模型 | DeepSeek `deepseek-flash`，真实调用（非 mock） |

> 这些限制不影响 L3 的结论（分析并发），因为那一层是 I/O 等待主导，
> 与网络带宽无关；但它确实限制了 L1/L2 数字作为"最大 QPS"的可引用性。
