## 1. M10.1 已完成（指标包 + counter）

| 项 | 结果 |
|---|---|
| 目录 schema | `metric_type` / `secondary_metric_type` / `extra_metrics`（JSON，最多 8 条） |
| counter 语义 | PromQL 自动包 `rate(metric[窗口/2])` |
| ecs-copilot 指标包 | `node_load1`(gauge) + 可用内存(gauge) + 磁盘 IO counter |
| 真实评测（M10.7 当前） | CPU / 内存 / 磁盘 **Rank1 3/3、Recall@3 3/3**，证据 **8/8 real** |
| 测试 | 218 / 218 OK（含 CMDB/审批/发现/管理页/DAG/认证/租户/CPU 指标） |

关键设计：

- 扩展指标必须是目录显式配置，不猜 metric 名；
- 只有扩展信号 ≥ 主指标变化的 5 倍且 ≥100% 时才生成确定性候选，
  防止 CPU 压力顺带抬高磁盘 IO 时误判；
- 过滤“暂无证据/无样本/不足以/排除”等非因果陈述，不让审计结论抢 Rank1。

## 3. CMDB 接口从哪里来

### 方案 A：自建轻量 CMDB + 发布服务（已采用）

FastAPI + MySQL，提供：

```
GET  /api/v1/services
GET  /api/v1/services/{name}/topology
GET  /api/v1/changes?service=...&window=...
POST /api/v1/changes        # 真实发布/配置变更登记
```

- 数据是真实持久化的注册表/变更单，不是 fixture；
- 与现有 MCP `cmdb.topology` / `deploy.changes` 协议完全兼容；
- 不需要外部账号，部署在 ECS/本机都行；
- 代价：不是商业 CMDB，面试时要说明是“平台自带轻量 CMDB”。

### 方案 B：开源 CMDB

| 项目 | 接口 | 适合度 |
|---|---|---|
| iTop（Combodo） | REST API | PHP+MySQL，较轻；适合服务/变更 |
| NetBox | REST API | DCIM/IPAM 强，服务拓扑弱；Postgres+Redis |
| 蓝鲸 CMDB（bk-cmdb） | REST API | 功能全但组件多，3.5 GB ECS 跑不动 |
| CMDBuild | REST API | Java/Tomcat/Postgres，重 |

### 方案 C：商业/云 CMDB

| 来源 | 接口 | 前提 |
|---|---|---|
| ServiceNow CMDB | `/api/now/table/cmdb_ci`、`/api/now/table/change_request` | 实例地址 + 账号/Token |
| 阿里云资源中心/ECS/RDS OpenAPI | `ListResources` / `DescribeInstances` 等 | RAM AccessKey；只有资源清单，无服务拓扑 |
| 腾讯云/华为云资源 API | 各自 OpenAPI | 同上 |

### 方案 D：服务注册中心（不是 CMDB）

Nacos / Consul / Kubernetes API 可提供“服务实例 + 健康”，但没有变更历史和
责任人/等级；可作为拓扑来源之一，不建议当完整 CMDB。

**建议**：P1 用方案 A；如果是要写“对接企业 CMDB”，你再给我 ServiceNow/iTop
的 base URL 和只读 Token，我按方案 C 适配。
