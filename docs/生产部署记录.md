```bash

systemctl restart copilot
```

SQLite 原文件保留在 `/opt/copilot/data/core.backup-sqlite.db`。

### 生产化取舍

- **单连接 + 全局锁**：所有模块共享一个 MySQL 连接，由 `Database.lock` 串行化。
  线程安全，但吞吐受限于单连接。要提升并发需换连接池（DBUtils / SQLAlchemy pool）。
- **写入延迟上升**：SQLite 本地写是微秒级，RDS 内网往返约 0.5–1 ms。
  对 LLM 主导的 15 秒分析链无感，但纯写接口 RPS 会下降。
- **租约可考虑迁 Redis**：`leases` 是高频短生命周期写入，是下一步最值得挪走的部分。

## 七点六、对象存储：阿里云 OSS 归档

**接入时间**：2026-11-22 02:30 CST

| 项 | 值 |
|---|---|
| Bucket | `copilot-artifacts-ly`（华东1 杭州，**私有**） |
| 冗余 | 本地冗余 LRS（匹配试用资源包，同城冗余 ZRS 不抵扣） |
| 端点 | `oss-cn-hangzhou-internal.aliyuncs.com`（**内网，不计流量费**） |
| 对象前缀 | `postmortems/{task_id}/` |
| 凭据 | RAM 用户 `copilot-oss` + 自定义策略 `CopilotOssArtifacts` |

### 权限设计

```json
{"Effect": "Allow",
 "Action": ["oss:PutObject", "oss:GetObject"],
 "Resource": ["acs:oss:*:*:copilot-artifacts-ly/*"]}
```

只允许**写、读**，且**限定这一个桶**。没有 List、没有 Delete、没有 FullAccess。
即使 AK 泄露，攻击面也只有"往一个桶里塞文件"。

### 归档内容

每次分析完成后自动上传三个对象：

| 文件 | 内容 | 典型大小 |
|---|---|---|
| `report.md` | Markdown 复盘报告 | ~1.3 KB |
| `report.docx` | Word 版本（含证据超链接） | ~38 KB |
| `evidence.json` | 全部证据原文与哈希 | ~2 KB |

对象键**确定性生成**（不含时间戳），重跑同一任务会覆盖自己的归档，不会堆积重复文件。

### 下载设计：代理而非签名 URL

**踩到的坑**：`bucket.sign_url()` 生成的 URL 基于构造 Bucket 时用的端点。
用 `-internal` 端点上传（省流量费），生成的签名 URL 就是
`copilot-artifacts-ly.oss-cn-hangzhou-internal.aliyuncs.com`——
**公网 DNS 解析不到，浏览器打不开**。

**做法**：`/tasks/{id}/archive/{kind}` 不重定向，而是由 API 从内网读对象再流式返回。
好处：

- 桶保持完全私有，无需开放公共读
- 不向浏览器暴露 OSS 主机名
- 内外网端点差异被完全隔离在服务端

### 验证结果

| 验证项 | 结果 |
|---|---|
| 裸测 AK（PUT/GET/签名） | PUT 200、GET 内容一致 |
| 分析后自动归档 | archive 表 3 条记录 |
| OSS 对象存在性（HEAD） | 3 个对象，字节数与 DB 完全一致（2071 / 38248 / 1348） |
| 报告页归档区块 | 存在，3 个下载链接 |
| 下载（走 API 代理） | 全部 HTTP 200，Content-Type 正确 |

### 已知限制

- 归档是**尽力而为**：OSS 失败只记日志，不影响分析结果返回（有测试守着这个行为）
- 未做**重试**：上传失败的对象不会自动补传，需重跑分析
- 未做**清理策略**：Bucket 未配置生命周期规则，对象会一直保留（20 GB 配额下够用）

## 七点七、长期记忆：ContextDB v3 记忆 API

**接入时间**：2026-11-22 20:20 CST

### 探测过程：三个错误假设都被推翻

| 假设 | 实测 | 结论 |
|---|---|---|
| 记忆接口是 `/v1/memories` | 403 `4007 route is not declared` | **v1 没有这个路由** |
| 用 Workspace API Key 能调记忆 | knowledge 200 / memories 403 | Key 只覆盖 knowledge/skill |
| OAuth Bearer 能解决 | 仍 403（v1 路径） | 认证不是唯一问题 |

**真正答案（从官方 npm 包 `@aliyunrds/ctxdb@1.1.0` 反查得到）：**

| 项 | 真值 |
|---|---|
| 记忆接口 | **`/v3/memories/add/`、`/v3/memories/search/`、`/v3/memories/`** |
| 认证 | **OAuth 会话令牌**（`Authorization: Bearer`） |
| OAuth 服务 | `https://api.cn-hangzhou.agentcontext.aliyuncs.com` |
| 授权流程 | RFC 8628 设备码（`/v1/auth/device/authorize` → 用户点链接 → `/v1/auth/device/token`） |
| client_id | `ctxdb-cli` |
| 令牌有效期 | **1800 秒**，需 `POST /v1/auth/token/refresh {refresh_token}` 续期 |

**关键判断**：文档只写了操作名（AddMemories/SearchMemories）没写路径，
按文档猜路径必然失败。**读官方客户端源码比反复试错高效一个数量级。**

### 实现

`services/core/app/memory.py`：

| 组件 | 作用 |
|---|---|
| `ContextDbMemory.remember()` | `POST /v3/memories/add/`，体为 `{messages:[{role,content}], user_id, agent_id}` |
| `ContextDbMemory.recall()` | `POST /v3/memories/search/`，体为 `{query, user_id, agent_id, top_k, threshold}` |
| `_do_refresh()` | token 过期前 60 秒或收到 401 时自动刷新，并把新 token 写回 `.env` |
| `strip_history_section()` | **写入前剥掉召回附录**（防反馈污染） |
| `history_section()` | 渲染为非证据附录 |

`scripts/ctxdb_device_login.py`：用 Python 实现设备码授权（不需要装 Node/CLI）。

### 原生记忆 vs 知识库载体的差异

实测召回结果中出现：

```
[2026-11-22] user: order-service v2.31 将连接池上限从 200 降到 50 ...
(Atomic facts: order-service 回滚至 v2.30 后支付链路恢复正常;
               order-service v2.31 连接池耗尽导致请求排队，P99…)
```

**ContextDB 会自动把一次复盘拆成多条原子事实**（实测 1 份报告 → 3 条事实），
这是知识库方案做不到的。

### 验证结果

| 验证项 | 结果 |
|---|---|
| 设备码授权 | 成功，取得 access + refresh token（scope=default） |
| 记忆写入 | 200 `{"status":"PENDING"}`，异步抽取 |
| 原子事实数 | 1 条记忆 → **3 条 atomic facts** |
| 语义检索 | **score 0.87 / 0.96 / 0.97** |
| 报告集成 | 「历史相似故障」附录，含非证据声明 |
| 测试 | **105 全绿**（新增记忆与防污染测试） |

### 修掉的一个真实缺陷：记忆反馈污染

**现象**：检索结果里出现了包含「## 历史相似故障」章节的记忆文档。

**原因**：写入记忆时传的是「已拼接召回附录的报告」——
于是第 N 次记忆里包含第 N-1 次的召回内容，逐轮叠加。

**修复**（两层）：
1. API 层传**原始报告**给 `remember()`
2. `remember()` 内部再调 `strip_history_section()` 兜底

**测试**：`test_remember_never_stores_appendix` 守着这个行为。

> 这类缺陷在长期记忆系统里是致命的：记忆越用越脏，最后每个新分析的输入里
> 都是前 N 次的历史，模型会被自己的旧结论淹没。**必须在写入侧解决，读取侧过滤来不及。**

### 已知限制

- **异步抽取**：写入后 5–10 秒才可检索；连续两次分析间隔过短会召不到
- **无去重**：同一服务反复分析会产生多条相似记忆（依赖服务端「记忆整理」能力，未启用）
- **token 30 分钟**：已实现自动刷新，但 refresh token 失效需重新走设备授权（人工点链接）
- **user_id/agent_id 是硬编码作用域**：多租户场景需要按请求隔离

## 七点十一、M10.4：通用 DAG + 局部重规划

**上线时间**：2026-11-23 18:40 CST

### 计划模型

```text
telemetry ┐
log       ├── 独立分支
change    ┘
impact    ← telemetry + change
review    ← telemetry + log + change + impact
```

- `TASK_PLANNED` 持久化 `depends_on`；
- 计划提交时校验重复 step / 未知依赖 / 环；
- 执行顺序由拓扑排序决定。

### 局部重规划

- 某 step 超过重试预算后标记 FAILED；
- 只把它的下游标记 `STEP_SKIPPED`，独立分支继续；
- 任务进入 `WAITING_HUMAN`，报告保留已完成分支的证据；
- 不把失败分支的证据伪造成成功。

### 分布式分配

`rendezvous hashing` 把 ready steps 稳定分配给 worker：

```text
telemetry -> w2
log       -> w1
change    -> w3
```

增删 worker 只重映射部分 key，不需要中心锁。真正的互斥仍由租约 + fence
保证，调度器只决定“谁优先处理”。

### 验证

```text

plan_dag.py 输出拓扑与分配
失败注入测试：telemetry 失败 -> impact/review SKIPPED，log/change SUCCEEDED
```

## 八、已知限制
| 限制 | 说明 |
|---|---|
| 单实例无高可用 | 实例故障即服务中断；生产应 ≥2 副本 + SLB |
| 无域名/HTTPS | 中国大陆 80/443 需 ICP 备案，当前用 `IP:8000` |
| 自建企业级 CMDB 已上线，但不是 ServiceNow/蓝鲸 | 已有 CI 图/审批/审计/RBAC/阿里云发现；接外部 CMDB 需按 v1 契约适配 |
| CMDB 为单实例 | 无多副本/跨可用区；后续 K8s/HA 阶段处理 |
| 阿里云发现覆盖 ECS/RDS/OSS/SLB/Redis | Config 时间线未接；多账号资源目录未接 |
| MCP 侧没有统一限流/熔断 | 当前只有 local registry 的限流；MCP 进程需补令牌桶 |
| 共享网关是单进程内的 | 多副本部署时每副本一套 MCP 子进程，下一步抽 sidecar/独立服务 |
| 影响面指标默认固定为 copilot 的 HTTP metric | 其他服务需要扩展 binding 的 impact metric 配置 |
| 真实评测只有 3 个场景、样本量小 | 只验证链路和方向，不作为统计结论 |
| 管理页只有 Basic Auth | 已接 OIDC（dev Keycloak）；无表单 CSRF token、未按服务限流 |
| 无集中日志 | 依赖 journald，未接 SLS |

这些不是缺陷，是**刻意的最小可行部署**，每一条都对应一个明确的升级触发条件。
