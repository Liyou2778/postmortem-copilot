## 1. 目标

M8 解决了“服务名 → 数据源”的可信映射，但还有四个明显短板：

| 问题 | M9 的做法 |
|---|---|
| 每次分析新建 6 个 MCP 子进程，冷启动 + 内存峰值 | 进程级共享网关 + 健康检查 + 网关指标 |
| 日志证据仍是 devstack Mock | ECS 部署 Loki + Promtail，采集 journald，接成真实数据源 |
| 没有应用级指标，影响面统计是空的 | 给 copilot 加 HTTP / 分析 / MCP 指标，Prometheus 抓取 |
| 评测只在 devstack 注入，没验证过真实遥测 | CPU / 内存 / 磁盘受控故障 + ground truth + 真实分析 |

## 2. 共享 MCP 网关（M9.1）

### 2.1 基线 vs 改造后（生产实测）

| 指标 | M8（per-run） | M9（shared） |
|---|---|---|
| order-service 分析耗时 | 21.76 s | **16.35 s** |
| 分析期间 MCP 进程数 | 6（每次新建） | **6（常驻，恒定）** |
| 服务内存峰值 | 306 MB | 303 MB |
| 冷启动次数 | 每个任务 6 次 | 进程启动时 1 次 |

> 耗时的其余部分是真实 LLM 调用，不能把 5.4 s 的差值全部归因于网关。

### 2.2 生命周期

```
app startup
  └─ shared_gateway(settings)          # 只创建一次
       ├─ open_all()                   # 6 个 stdio server 并发启动
       ├─ health monitor thread        # 每 30s send_ping
       │    └─ dead server → close + reopen（per-server lock）
       └─ run_coroutine_threadsafe     # 所有分析共享同一 event loop
app shutdown
  └─ close_shared_gateway()            # 停 monitor、关会话、停 loop
```

关键设计：

- `MCP_GATEWAY_MODE=shared`（默认）/ `per_run`（回滚）。
- `MCP_HEALTH_INTERVAL_S=30`；0 关闭健康检查。
- 单个 server 重启有独立锁，不会阻塞其他 5 个。
- `send_ping` 失败才重启；工具返回业务错误不触发重启。
- 启动预热在 FastAPI `startup`，故障在用户发请求前就暴露在 journald。

### 2.3 每任务审计隔离

共享网关的 `audit` 是进程级列表。直接沿用会让任务 B 的报告出现任务 A 的工具调用（第一次生产验证确实出现了 `tools=8` 而不是 5）。

修复：`AuditedTools` 包装器，在本任务内记录 `AuditRecord`，底层网关仍保留全局审计/指标。

### 2.4 指标

```
copilot_mcp_server_up{server="prometheus"} 1
copilot_mcp_server_restarts_total{server="..."}
copilot_mcp_tool_calls_total{server="...",tool="...",ok="true"}
copilot_mcp_tool_latency_seconds{server="...",tool="..."}
```

## 3. 真实 Loki 日志（M9.2）

### 3.1 组件

| 组件 | 版本 / 地址 | 说明 |
|---|---|---|
| Loki | 2.9.8，`127.0.0.1:3100`（gRPC 9096） | 单节点，filesystem + boltdb-shipper，7d retention |
| Promtail | 2.9.8，`127.0.0.1:9080` | 读 journald，推送本地 Loki |
| 采集范围 | `unit=copilot.service` | copilot 及其 MCP 子进程日志 |
| 安全 | 两个服务仅监听本机 | 安全组未开放 3100/9080 |

安装脚本：`scripts/install_loki.sh`。GitHub 直连慢时可先在代理机器下载
`loki-linux-amd64.zip` / `promtail-linux-amd64.zip`，scp 到 `/tmp/loki-2.9.8.zip`
和 `/tmp/promtail-2.9.8.zip`，脚本会优先使用预置包。

### 3.2 踩到的两个真实问题

| 问题 | 现象 | 修复 |
|---|---|---|
| Loki 查询挂死 | gRPC 只绑 127.0.0.1，但 query scheduler 广播 ECS 私网 IP 172.24.x.x，反复 dial 自己失败 | gRPC 绑 `0.0.0.0`（VPC 内，不对公网），HTTP 仍绑 127.0.0.1 |
| 日志证据自指 | MCP server 的 httpx INFO 日志包含完整 LogQL，LogAgent 的 error 正则匹配到自己的查询 | MCP 子进程关闭 `httpx/httpcore/mcp` INFO；Loki 查询加 `!~ "loki/api/v1\|Processing request of type"` 负过滤 |

### 3.3 接入服务目录

```
datasource: ecs-loki   kind=loki   base_url=http://127.0.0.1:3100   mock=false
binding:    ecs-copilot/loki → ecs-loki
            selector = job="journal",unit="copilot.service"
            mode = real
```

`CatalogRouter` 注入 `datasource_url`、`selector`、`data_mode`；Loki MCP server
支持字面量 `|=` 和 `re:` 正则 `|~`，真实日志证据因此进入报告。

验证：`scripts/probe_loki.py` 返回 `job/level/unit` labels 和真实 journald 行。

## 4. 应用指标与影响面（M9.3）

### 4.1 新增指标

| 指标 | 标签 | 用途 |
|---|---|---|
| `copilot_http_requests_total` | method / path(route template) / status | 请求速率、5xx |
| `copilot_http_request_duration_seconds` | method / path | P95 延迟 |
| `copilot_analysis_total` | service / status | 分析成功/失败 |
| `copilot_analysis_duration_seconds` | service | 分析耗时 |
| `copilot_mcp_server_up` / `tool_calls` / `latency` | server / tool | 网关观测 |

`/metrics` 自身被排除，避免 scrape 污染；path 用 FastAPI route template，避免
每个 task UUID 生成一条时间序列。

Prometheus 新增 job：

```yaml
- job_name: copilot
  static_configs:
    - targets: ["127.0.0.1:8000"]
      labels:
        service: ecs-copilot
        instance_name: copilot-api
```

### 4.2 影响面工具

`prometheus.impact`（MCP）执行四组 PromQL：

| 维度 | PromQL |
|---|---|
| 请求速率 | `sum(rate(copilot_http_requests_total{selector}[1m]))` |
| 5xx 错误率 | `(sum(rate(...status=~"5.."[1m])) or vector(0)) / clamp_min(sum(rate(...[1m])), 1e-6)` |
| P95 | `histogram_quantile(0.95, sum(rate(..._bucket[1m])) by (le))` |
| 可用目标 | `sum(up{selector})` |

窗口与基线取等长的相邻两段；返回 `queries`（PromQL 原文）、`summary`、
`impact`、`errors`、`no_data`。NaN（无 histogram 样本）会被过滤，否则 MCP
JSON 序列化会整体失败；这是第一次联调时踩到的。

### 4.3 报告与证据

- `ImpactAgent` 只接受 `data_mode=real`；Mock/fixture 直接跳过，不生成假数字。
- 新增 `SourceKind.IMPACT` 证据 `E-IMP-001`，含请求峰值/5xx/P95/目标数 + PromQL。
- 报告新增「三、影响面」章节，表头：指标 / 故障窗口 / 基线 / 变化。
- 影响面数字与查询语句在同一份报告里，满足 FR-6 的“可追溯到原始查询”。

## 5. 真实 Prometheus 评测（M9.4）

见 `docs/真实Prometheus评测.md`。3 个主机级受控故障，真实分析链，关键词打分：

| 场景 | Rank1 | Recall@3 | 真实证据 | 影响面 |
|---|---|---|---|---|
| CPU | ✅ | ✅ | 5/5 | ✅ |
| 内存 | ✅ | ✅ | 5/5 | ✅ |
| 磁盘 | ✅ | ✅ | 5/5 | ✅ |

**M10.1 补齐指标包后总体 Rank1 = 3/3，Recall@3 = 3/3。**

> M10.7 在 K8s + Chaos 环境复跑：Rank1 3/3、Recall@3 3/3；影响面 3/3 存在、
> 证据 8/8 real。中间 2/3 的回归过程保留在文档中，最终通过 CPU 利用率
> 指标修复 CPU 场景。

原始 M9 评测磁盘场景是 0/3，原因是绑定只有 `node_load1` + 可用内存，没有
`node_disk_io_time_seconds_total` 这类 counter。M10.1 增加 gauge/counter 语义
和扩展指标包后，磁盘 IO 以 `rate()` 进入 Telemetry；再加“扩展指标显著强于主
指标时生成确定性候选”的规则，磁盘 Rank1 变为 ✅。这不是调关键词，而是补输入。

评测还暴露并修复了两类产品缺陷：

- 非因果结论（“暂无证据支持…”、“磁盘 IO 极低不足以解释…”）靠高置信度抢占
  Rank1；过滤后 CPU/内存 Rank1 恢复；
- 扩展指标不能无条件升级为根因：CPU 压力也会扰动磁盘 IO，因此要求扩展信号
  ≥ 主指标变化的 5 倍才生成确定性候选。

## 7. 已知限制

| 限制 | 说明 |
|---|---|
| 共享网关是单进程内的 | 多副本部署时每副本各有一套 MCP 子进程；下一步抽成独立 sidecar/服务 |
| 健康检查只 ping，不验证业务工具 | ping 失败会重启，工具级超时仍由调用方处理 |
| 影响面指标默认固定为 copilot 的 HTTP metric | 其他服务需要扩展 binding 的 impact metric 配置 |
| P95 包含 `/run` 这类长耗时接口 | 会抬高“服务 P95”；后续按 route 分组或排除分析接口 |
| 真实评测样本只有 3 个 | 只用于验证链路与方向，不能当统计结论 |
| Loki/Promtail 单机 | 无副本、无对象存储后端，日志量上来后需迁 S3/OSS |
